# V1.3.3 YouTube research intelligence

This milestone turns an existing normalized `CollectionResult` into an explainable in-memory research report. It adds no persistence, LLM calls, new ingestion contracts, dashboard features or changes to legacy ranking. Scores are TrendScout research heuristics, not YouTube-published metrics, recent growth measurements, predictions of virality/profitability or validated market demand.

## Usage and authorization

```powershell
# Synthetic offline report: no credentials or network.
.\.venv\Scripts\python.exe -m trendscout.ingestion.youtube_intelligence --query "AI automation" --limit 10 --fixture

# Only after applicable live analytics authorization has been established:
.\.venv\Scripts\python.exe -m trendscout.ingestion.youtube_intelligence --query "AI automation" --limit 10 --authorized-live-analysis

# Override the transparent weights and freshness half-life:
.\.venv\Scripts\python.exe -m trendscout.ingestion.youtube_intelligence --query "AI automation" --fixture --freshness-weight 0.4 --views-weight 0.3 --likes-weight 0.2 --comments-weight 0.1 --half-life-days 14
```

Live mode reuses V1.3.2's environment configuration, bounded pagination, timeouts and quota handling. There is no silent fixture fallback. Without `--fixture` or `--authorized-live-analysis`, the command stops before constructing a client or spending quota. The Python analysis entry point similarly requires `authorized_live_analysis=True` for live-provenance results and rejects unknown provenance.

An API key or a successful API request alone does not establish authorization for derived analytics. YouTube's [Developer Policies III.E.4.h and III.L](https://developers.google.com/youtube/terms/developer-policies) restrict derived data and describe the additional permission process. The [derived-metrics policy](https://developers.google.com/youtube/terms/derived-metrics-policy) makes eligible analytics conditional on acceptance of the applicable amendment. The switch is the caller's explicit acknowledgment of applicable authorization, not a permission grant or automatic verification. It does not enable retention.

Per the maintainer's report, the V1.3.2 live ingestion smoke test succeeded on **October 17, 2026**. This milestone's verification is offline and does not repeat a live request. Production readiness, permission for the intended analytics use, and live-data retention remain unverified.

## Modules and contracts

| Module | Responsibility |
| --- | --- |
| `intelligence/models.py` | Validated configuration, signals, components, completeness, opportunities and report models. |
| `intelligence/youtube.py` | Canonical validation, deterministic signals, ranking and source-grounded lenses. |
| `ingestion/youtube_intelligence.py` | Read-only terminal report, explicit fixture/live modes and weight options. |

```python
from trendscout.intelligence.models import RankingConfig
from trendscout.intelligence.youtube import analyze_collection

# `result` is an existing synthetic CollectionResult, not a raw API response.
report = analyze_collection(result, RankingConfig())
```

Input is revalidated, including nested metrics. Malformed counters or an inconsistent canonical batch produce a static error without payload details or serializer warning leaks. Other-platform/non-video records and expired source records are explicitly excluded. Expired observations are unavailable. Failed collections yield an empty report with failure caveats; partial collections retain accepted eligible records and identify sampling limitations.

## Signals and time semantics

The default report time is the collection's UTC completion time; there is no hidden clock in analysis. Python callers may supply an aware `as_of` at or after completion. Naive timestamps or an earlier report time are rejected.

| Signal | Definition and missing-value behavior |
| --- | --- |
| Video age | `(as_of - published_at) / 86400 seconds`. Missing/future publication yields `None`, with a caveat; future dates receive no freshness credit. |
| Observation age | `(metrics.observed_at - published_at) / 86400 seconds`, independent of later report time. |
| Lifetime average views/day | `observed views / observation age`, only for positive elapsed exposure. It is **not measured recent velocity**. Zero elapsed time, missing views/date or inconsistent chronology yields `None`. |
| Like/view ratio | Observed likes divided by positive observed views. Missing counters or zero views yield `None`; zero likes with positive views yields actual zero. |
| Comment/view ratio | Observed comments divided by positive observed views, with the same availability rules. No comment text, sentiment or viewer intent is inferred. |
| Freshness | `100 × 2^(-video_age_days / half_life_days)`, default half-life 30 days. |

Publication after the observation makes derived engagement unavailable. Future publication makes all derived engagement unavailable while preserving raw supplied counters as evidence. Ratios above one are retained as arithmetic ratios and flagged, not treated as probabilities. Small view denominators receive an instability warning. Single observations cannot establish growth, acceleration or a historical trend.

Completeness lists available/missing fields among title, description, creator, publication time, views, likes and comments. Its fraction is available fields divided by seven; a known zero counter is available. Completeness is not an accuracy score and is not a bonus in ranking.

## Explainable priority ranking

Four bounded components contribute to a 0–100 **research priority score**:

| Component | Default weight | Normalization |
| --- | --- | --- |
| Freshness | 0.30 | Time-decay score above. |
| View evidence | 0.35 | `100 × x / (x + 1000)`, where `x = views / max(observation_age_days, 1)`. |
| Like ratio | 0.20 | `100 × ratio / (ratio + 0.05)`. |
| Comment ratio | 0.15 | `100 × ratio / (ratio + 0.01)`. |

The one-day exposure floor stabilizes **view scoring only**. The separately reported lifetime average retains its actual elapsed-time denominator and is flagged for short exposure. Raw lifetime view counts are not directly scored or min-max compared across videos of different ages.

All weights must be finite and nonnegative, with at least one positive weight. Weights are divided by their total once. The overall score sums available component scores times those fixed normalized weights. Missing scores remain `None`, contribute no credit, and **never cause their weights to be redistributed**. If every enabled component is unavailable, the overall score is `None`, not zero. Known zero components remain distinguishable from unavailable ones.

Configuration also exposes positive finite exposure floor, half-life and saturation references through `RankingConfig`. These defaults are transparent choices for research triage, not empirically validated thresholds. No batch-relative normalization means adding a competitor does not change an existing item's component score. Sort by unrounded priority descending, unavailable priorities last, then source ID and case-sensitive native external ID. Assign one-based ranks after sorting. Identical inputs, configuration and report time give identical reports, independent of item input order.

Each item contains component scores, normalized weights, explicit availability, formula explanations, weighted contribution explanation, evidence timestamps and caveats. The CLI rounds only displayed values.

### Synthetic worked example

For an explicitly hypothetical video with a 10-day age at observation, 1,000 views, 50 likes and 10 comments:

- Lifetime average: 100 views/day; like/view ratio 0.05; comment/view ratio 0.01.
- Freshness: approximately 79.37; view evidence: 9.09; both ratio components: 50.
- Default priority: `0.30×79.37 + 0.35×9.09 + 0.20×50 + 0.15×50 ≈ 44.49`.

This is a calculation example, not collected video history. Packaged fixture dates are fixed, so its displayed freshness varies with the collection timestamp. A newer and older video with the same lifetime average receive equal view-evidence components; freshness remains separate. An older snapshot analyzed later retains its original lifetime average and is labeled as an older observation.

## Two separated opportunity lenses

**Creator intelligence** proposes a worked example or, when an observed positive comment/view ratio exists, a question-and-answer walkthrough. Topic cues come only from bounded quoted title/description text. It preserves observed-ratio evidence and explicitly leaves audience preference, comment topics and viewer intent unknown.

**Business intelligence** proposes an **unvalidated research hypothesis** that people exploring the quoted workflow/topic may have questions. Its next step is interviewing intended users and checking whether recurring problems exist. Metadata alone cannot establish customer pain, willingness to pay, competitive gaps or market demand. The video priority score is never labeled a business-demand score.

Rules are deterministic whole-word keyword cues with a neutral source-topic fallback. They do not execute quoted instructions or promote source claims to verified facts. If title and description are unavailable, hypotheses remain `None`. Source excerpts are bounded and CLI-quoted to escape control characters. Source URLs/IDs remain available for manual review.

## Read-only behavior, limitations and verification

The new modules do not instantiate SQLite, invoke exporters or write live metadata, derived per-video reports or raw responses. The command prints to the terminal; user-controlled redirection, external logging and terminal history are outside its persistence controls. No retention switch is provided. Existing source-specific persistence safeguards remain unchanged.

This report is research triage over a bounded search sample. Search order, omitted/private counters, video age, small denominators, stale observations and source selection can affect interpretation. There is no recent-period measurement, calibrated probability, statistical confidence interval, Shorts classification, LLM inference or validation of either opportunity lens. Production analytics and live retention need separate review.
