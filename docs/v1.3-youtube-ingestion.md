# V1.3.2 YouTube ingestion

The YouTube adapter implements V1.3.1's `IngestionSource` protocol using the official Data API v3 and the existing `requests` dependency. It collects bounded public video metadata and native counters into `CollectionResult` objects. Collection is independent of SQLite persistence, legacy Reddit discovery, ranking, generation and the Streamlit dashboard. No shared models, protocols or export schemas change.

**Live ingestion smoke-tested October 17, 2026**, as reported by the maintainer after V1.3.2 implementation. Automated tests remain offline. Production readiness, intended analytics permissions and live-data retention remain unverified.

## Architecture and request flow

| File | Responsibility |
| --- | --- |
| `ingestion/youtube.py` | Environment configuration, HTTP client, normalization and `YouTubeSource`. |
| `ingestion/youtube_fixture.py` | Explicit offline response provider, without an HTTP transport. |
| `data/youtube_fixture.json` | Three packaged synthetic records, including absent statistics. |
| `ingestion/youtube_demo.py` | Read-only collection command and concise terminal summary. |
| `tests/ingestion/test_youtube.py` | Mocked API, normalization, CLI and retention integration tests. |

1. Validate `CollectionRequest` (query, source identity, candidate limit 1–100).
2. Call [`search.list`](https://developers.google.com/youtube/data/reference/rest/v3/search/list), `GET https://www.googleapis.com/youtube/v3/search`, with `part=snippet`, `type=video`, `q` and `maxResults` up to 50. Request only video identities and the next-page token through `fields`.
3. Deduplicate IDs across pages, then call [`videos.list`](https://developers.google.com/youtube/data/reference/rest/v3/videos/list), `GET https://www.googleapis.com/youtube/v3/videos`, in batches of at most 50 IDs. Use `part=snippet,statistics` and an allowlisted `fields` selector. No `maxResults` or pagination token is sent to ID-based details requests.
4. Validate and normalize individual details, retaining valid siblings if another record is malformed. Missing details are rejected without guessing whether a video is private, deleted or otherwise unavailable.
5. Return an attributed canonical result. Live source identity is `youtube.data-api-v3`; fixture identity is `youtube.fixture`. Each result has a new run UUID and UTC start/completion times; records and observations use the time their details batch was received.

The limit is a bounded **candidate budget**, including rejected records, rather than a promise of that many valid videos. Duplicates do not consume extra identities. No additional searches backfill malformed candidates after the budget is exhausted. Fewer results can be legitimate when search is exhausted. A remaining next-page token at the configured cap is explicitly partial. Partial results keep earlier accepted videos when a later request fails. Rejection counts cover observed malformed records or missing details; IDs whose details could not be fetched due to an API failure are not counted as malformed. If errors occur without accepted items, status is failed. Missing credentials and mismatched source requests raise curated collection exceptions before collection; normal API failures become explicit result error codes.

## Credentials and environment

Follow Google's [YouTube credential setup](https://developers.google.com/youtube/registering_an_application): select/create a Google Cloud project, enable YouTube Data API v3, and create an API key for public-data requests. Restrict the key to that API and appropriate application restrictions. This adapter does not implement OAuth or retrieve private account data.

Configure locally in environment variables or the ignored `.env` file. Existing environment values take precedence over `.env`. Do not commit keys or paste them into commands that expose shell history.

| Variable | Default | Bounds |
| --- | --- | --- |
| `YOUTUBE_API_KEY` | Absent; live collection fails clearly | Required for live mode only |
| `YOUTUBE_MAX_SEARCH_PAGES` | 2 | 1–5 |
| `YOUTUBE_DETAILS_BATCH_SIZE` | 50 | 1–50 IDs |
| `YOUTUBE_MAX_ATTEMPTS` | 3 | 1–3 total attempts per HTTP request |
| `YOUTUBE_CONNECT_TIMEOUT` | 5 seconds | Greater than 0, at most 120 |
| `YOUTUBE_READ_TIMEOUT` | 20 seconds | Greater than 0, at most 120 |

Keys use a masked Pydantic `SecretStr` and the `X-Goog-Api-Key` header, not a URL parameter, following [Google's REST API-key guidance](https://docs.cloud.google.com/docs/authentication/api-keys-use). Redirects are disabled to avoid forwarding that header. The adapter does not log credentials, response bodies or raw transport exception text. Do not enable external HTTP header tracing with real credentials.

## Commands

From the repository root after the existing editable installation:

```powershell
# Explicit offline mode: no Google key, network or database required.
.\.venv\Scripts\python.exe -m trendscout.ingestion.youtube_demo --query "AI automation" --limit 10 --fixture

# Live request: run only when authorized and intentionally choosing to spend quota.
.\.venv\Scripts\python.exe -m trendscout.ingestion.youtube_demo --query "AI automation" --limit 10
```

Fixture mode ignores live environment configuration, uses the same normalization/result contracts, and labels all three records synthetic. Its query does not imply discovery or niche relevance. Fixture video URLs point to `example.com`, not purported live YouTube videos. No live error substitutes fixture data.

The command prints source, status, accepted/rejected counts, UTC collection interval and at most three normalized records. It writes no source data, database or export file. Source text is JSON-quoted to escape terminal control characters. Exit codes are 0 for complete, 1 for partial/failed collection or credential errors, and 2 for invalid arguments/configuration. A complete empty search is a valid zero-result collection.

## Normalization

| API field | Canonical field |
| --- | --- |
| `id` | `external_id`, with `platform=youtube` |
| `snippet.title` / `description` | `title` / optional `description` |
| `snippet.channelTitle` | Optional `creator` |
| `snippet.publishedAt` | UTC `published_at`, distinct from collection time |
| Video ID | Public `https://www.youtube.com/watch?v=<id>` attribution URL |
| `statistics.viewCount` | Native counter `views` |
| `statistics.likeCount` | Native counter `likes` |
| `statistics.commentCount` | Native counter `comments` |

Details require a valid ID, nonblank title and aware publication timestamp. Optional fields remain absent if not returned. Missing statistics produce `metrics=None`; missing/null individual statistics remain `None`. Explicit zero counts remain zero. Decimal counter strings are parsed as nonnegative integers and checked against the existing signed-64-bit counter bound. Invalid counters reject that video; no clamping, imputation or cross-metric substitution is performed. Unknown provider fields are discarded, not persisted as a raw payload.

Content type remains `video`. Duration is deliberately not requested because the canonical contract has no duration field. There is no inferred Shorts classification, transcript retrieval, comment-body retrieval, media download or source-to-legacy-score conversion.

## Quota and error safeguards

Quota guidance was checked against official documentation on **2026-10-17**. The current [search method reference](https://developers.google.com/youtube/data/reference/rest/v3/search/list) lists one unit per call in its Search Queries bucket, with a default daily allocation of 100 search calls. The [videos method reference](https://developers.google.com/youtube/data/reference/rest/v3/videos/list) lists one unit per call. Google's [quota calculator](https://developers.google.com/youtube/data/determine_quota_cost) describes separate search quota and a default shared 10,000-unit daily allocation for other endpoints. Additional pages and retried requests consume quota. Check the Cloud console and current references for your project; these defaults are not runtime guarantees or a hardcoded budget ledger.

Default configuration permits at most two search and two details calls per collection, before retries. With up to three attempts each, that is at most 12 transport attempts. More conservative page/attempt limits can be configured. With the smallest configurable details batch, at most 100 details requests are possible; the overall absolute cap is `3 × (5 + 100) = 315` attempts. Empty/duplicate pages cannot exceed the search cap, and repeated page tokens stop collection. No account-wide quota tracking or background retry scheduler is implemented.

Timeouts, connection failures and HTTP 500/502/503/504 retry with bounded 1- and 2-second backoff. HTTP 429 and recognized quota/rate-limit reasons stop immediately without sleeping or retrying, including quota errors reported on a transient status. Authentication/permission errors, other HTTP errors, redirects, malformed JSON and invalid response envelopes are not retried. Error codes use the existing curated `access_denied`, `rate_limited`, `unavailable` and `invalid_response` vocabulary, plus explicit record/pagination issue codes. Response bodies and provider error messages never appear in summaries. See the [official API error reference](https://developers.google.com/youtube/data/reference/rest/v3/errors).

## Persistence and retention

The collection command has no persistence flags and does not instantiate `IngestionRepository`. Python callers can inspect results without retaining them. Repository rules are unchanged: a source-specific positive retention policy is mandatory, `allow_live` defaults to false, and unknown provenance cannot be stored. A policy for `youtube.fixture` does not authorize `youtube.data-api-v3`.

Do not enable live YouTube persistence until applicable API terms and the intended use have been reviewed. **Retention configuration is not proof of permission to store YouTube data or derive analytics from it.** Review the current [Developer Policies](https://developers.google.com/youtube/terms/developer-policies), particularly storage/refresh, deletion and derived-data restrictions. This milestone assigns no universal YouTube retention allowance, enables no automatic live persistence, and does not connect these counters to ranking or business-intelligence calculations.

For explicitly permitted persistence, existing repository TTL/deadline enforcement, expired-read filtering and `purge_expired()` apply. No raw API responses, API keys or queries belong in stored metadata. Tests exercise opt-in persistence only with mocked records and temporary/in-memory databases, then verify expiration cleanup. As documented in the [foundation reference](v1.3-ingestion-foundation.md), minimal operational run summaries can remain after source data expires; that audit retention also needs review for a deployment.
